# 012 — a draft index for RAG queries, and an async `list_documents`

**Scope:** `doc-hierarchy` only.
**Relates to:** `004`/`009` (`getCurrentDraftDir`, `workspaceRoot`), `005` (`apply_change`,
the "draft starts as a clean copy of its baseline" property), `008` (`approveBaseline`'s
next-draft creation step), `011` (the blue/green pattern and `processInBatches`, both reused
here, not reinvented).

**Two unrelated fixes bundled here because they came out of the same conversation:**
1. `ask_documents`/`suggest_changes` can only ever see the baseline — there's no way to ask "what
   does the *draft* currently say" at all. This adds a third index, scoped to draft content only.
2. `list_documents` does its file comparisons synchronously, in a loop, blocking the whole MCP
   server process while it runs — fine at 5 files, a real problem at hundreds.

**Index budget, now final rather than a trade-off**: `doc-hierarchy-index-blue` +
`doc-hierarchy-index-green` (from `011`) + this doc's `doc-hierarchy-draft-index` = 3, the
entire free-tier cap, deliberately, with `docs-index` having been dropped to make room and
`wiki-freshness` dropped so nothing is left contending for the slot this uses.

---

## Key design decisions (and why)

- **A separate physical index, not a field added to the baseline index.** The whole reason
  `004` removed the ability to index anything but the baseline was that sharing one index
  between baseline and draft content under the same `docId` is exactly what caused documents to
  overwrite each other. A separate index keeps that fix intact — there's no shared `docId` space
  for the two to collide in, by construction.
- **No blue/green for the draft index.** The baseline needs zero-downtime swaps because it's the
  thing being treated as ground truth under active query load. A draft is inherently
  work-in-progress — a few seconds of staleness immediately after an edit, while the index
  catches up, is a reasonable trade against spending a fourth index slot that doesn't exist.
- **Updated per-document, not per-cycle.** `apply_change` always knows exactly which one
  document it just touched — the natural hook is "re-embed just that document into the draft
  index right after a successful edit," not a full reindex pass. No content-hash comparison
  needed here either, unlike `011`'s baseline logic — there's nothing to compare against, the
  changed document is already known precisely.
- **Seeded by copying the baseline's chunks, not re-embedding, when a new draft cycle starts.**
  A fresh draft is byte-identical to the baseline it was just promoted from (the "clean slate"
  property from `005`) — so its initial index content can be *copied* from the
  just-reindexed baseline the same way `011`'s blue/green swap already copies unchanged
  documents between physical indexes, rather than re-embedded from scratch.
- **Kept out of `applyChange.ts` itself.** That module is pure OOXML surgery and doesn't know
  about `rag-api` or indexing — matching its existing scope, the draft-index update happens as a
  separate step in `mcpServer.ts`'s tool handler, after `applyChange()` succeeds, not inside it.
- **`processInBatches` (from `011`) is promoted to its own small shared module** now that a
  second caller (`list_documents`) needs it — not duplicated a second time.
- **Result ordering matters and isn't automatic under concurrency** — `list_documents`'s output
  needs to stay in a stable, predictable order regardless of which file comparison happens to
  finish first within a batch. Handled by writing into a pre-sized array by index, not by
  pushing to a shared array from concurrent callbacks (which would silently scramble the order).

## Open decision (not resolved here)

- **Adding or removing a whole document from the corpus mid-cycle** isn't handled by this or by
  anything else built so far — the draft index (like the baseline index) has no logic for a
  `docId` disappearing or appearing outside the normal promote/edit cycle. Not new to this
  change, just newly relevant since a second index now needs to stay in sync too.

|---|---|---|---|
| 1 | Create `doc-hierarchy-draft-index`, same schema as the baseline index | one-off script, reusing `011`'s `HIERARCHY_INDEX_SCHEMA` | One schema definition, three physical indexes total |

| 7 | Rewrite `list_documents`'s file comparison to be async and batched | `mcpServer.ts` | Removes the synchronous-loop blocking-the-whole-server problem at file-count scale |

## Code

### Steps 2, 4 — `doc-hierarchy/src/draftIndex.ts` (new)

```ts
import path from "node:path";
import { SearchClient, AzureKeyCredential } from "@azure/search-documents";
import { getCurrentDraftDir } from "./baselines.js";

const DRAFT_INDEX = "doc-hierarchy-draft-index";
const BASELINE_LIVE_INDEX_LOOKUP = () => import("./indexAlias.js").then(m => m.getLiveAndStagingIndexNames());

const credential = new AzureKeyCredential(process.env.AZURE_SEARCH_KEY!);
function clientFor(indexName: string) {
  return new SearchClient<HierarchyDoc>(process.env.AZURE_SEARCH_ENDPOINT!, indexName, credential);
}

function odataEscape(s: string): string {
  return s.replace(/'/g, "''");
}

/** Re-embeds one document into the draft index — called right after a successful apply_change. */
export async function updateDraftIndexForDoc(docId: string): Promise<void> {
  const filePath = path.join(getCurrentDraftDir(), `${docId}.docx`);
  const meta = await parseFile(filePath); // same parseFile as ingest.ts

  const client = clientFor(DRAFT_INDEX);
  const stale = await client.search("*", { filter: `docId eq '${odataEscape(docId)}'`, select: ["id"] });
  const staleIds: string[] = [];
  for await (const r of stale.results) staleIds.push(r.document.id);
  if (staleIds.length) await client.deleteDocuments("id", staleIds);

  await uploadDoc(meta, DRAFT_INDEX); // same uploadDoc as 011, target index parameterized
}

/** Seeds the draft index from the baseline's current live index — called once, right after a
 *  new draft is created, since the draft starts byte-identical to that baseline. */
export async function seedDraftIndexFromBaseline(docIds: string[]): Promise<void> {
  const { live } = await BASELINE_LIVE_INDEX_LOOKUP();
  const liveClient = clientFor(live);
  const draftClient = clientFor(DRAFT_INDEX);

  const existing = await draftClient.search("*", { select: ["id"] });
  const existingIds: string[] = [];
  for await (const r of existing.results) existingIds.push(r.document.id);
  if (existingIds.length) await draftClient.deleteDocuments("id", existingIds);

  for (const docId of docIds) {
    const results = await liveClient.search("*", { filter: `docId eq '${odataEscape(docId)}'` });
    const docs: HierarchyDoc[] = [];
    for await (const r of results.results) docs.push(r.document);
    if (docs.length) await draftClient.uploadDocuments(docs);
  }
}

export { DRAFT_INDEX };
```

### Step 6 — `doc-hierarchy/src/concurrency.ts` (new — extracted from `011`)

```ts
export async function processInBatches<T>(
  items: T[], batchSize: number, fn: (item: T) => Promise<void>
): Promise<void> {
  for (let i = 0; i < items.length; i += batchSize) {
    await Promise.all(items.slice(i, i + batchSize).map(fn));
  }
}
```
`ingest.ts` (`011`, step 14) imports this instead of defining it locally.

### Step 7 — `mcpServer.ts`, `list_documents`

```ts
import { processInBatches } from "./concurrency.js";
import fs from "node:fs";

async function compareFiles(baselineFile: string, draftFile: string): Promise<string> {
  const [baselineExists, draftExists] = [fs.existsSync(baselineFile), fs.existsSync(draftFile)];
  if (!baselineExists || !draftExists) return `missing (${!baselineExists ? "baseline" : "draft"})`;
  const [a, b] = await Promise.all([fs.promises.readFile(baselineFile), fs.promises.readFile(draftFile)]);
  return a.equals(b) ? "same" : "CHANGED";
}

// inside the list_documents handler, replacing the old synchronous loop:
const graphWithIndex = graph.map((g, i) => ({ ...g, i }));
const rows = new Array<string>(graph.length);
await processInBatches(graphWithIndex, 10, async ({ docId, i }) => {
  const result = await compareFiles(
    path.join(baselineDir, `${docId}.docx`),
    path.join(resolvedDraftDir, `${docId}.docx`)
  );
  rows[i] = `${docId}: ${result}`;
});
return { content: [{ type: "text" as const, text: rows.join("\n") }] };
```
Results are written into a pre-sized array by original index, not pushed to a shared array from
inside the concurrent callbacks — otherwise whichever comparison happens to finish first within
a batch would determine output order, not the graph's actual order.

## Known risks / not exercised

- **None of `draftIndex.ts` has been run** — the copy-from-live seeding logic in particular
  leans on `011`'s alias-lookup code, which is itself unexercised as of that doc.
- **`updateDraftIndexForDoc` runs synchronously inside `apply_change`'s response path** — if
  embedding a large document takes real time, the tool call itself now takes longer. Worth
  reconsidering as fire-and-forget (with the caller told the index update is in flight, not
  necessarily done) if `apply_change`'s response latency becomes noticeable at larger documents.
- **The batch size (`10`) in step 7 is an arbitrary starting point**, not tuned against real file
  I/O characteristics at any particular scale.
