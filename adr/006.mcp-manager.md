# 006. MCP Manager: Local Dev Server Supervisor

**Status:** Proposed
**Context:** `hackathon/mcp-rag-hackathon` monorepo (npm workspaces: `rag-api`, `docs-search`, `doc-hierarchy`)

## 1. Problem

During dev, `docs-search` and `doc-hierarchy` (and `rag-api`, which they call over HTTP) get edited constantly. Right now, picking up a change or recovering from a crash means fully quitting and relaunching Claude Desktop, which kills every open conversation. There's no way today to ask Claude, mid-chat, "what MCP servers are running?" or "restart doc-hierarchy."

## 2. Reality check first (important — read before building)

Verified against current Claude Desktop behavior: when a stdio MCP server process dies or is updated, Claude Desktop shows "Not connected" and **does not** reconnect on its own — not even when you start a new conversation. The only documented recovery today is fully quitting and reopening the app. There's an open feature request for a per-server "Refresh" button, but it doesn't exist yet.

That means a tool that just kills a server's OS process and calls it a "restart" doesn't actually work — Desktop's own connection to that process is now permanently broken until you relaunch the whole app, which is the exact pain we're trying to remove.

**So `mcp-manager` doesn't ask Desktop to reconnect anything.** Instead, it becomes the *only* thing Desktop connects to, and it owns the downstream servers itself:

- Claude Desktop opens **one** stdio connection to `mcp-manager` when it launches, and only fetches its tool list **once**, at that moment.
- `mcp-manager` spawns `docs-search` and `doc-hierarchy` itself as child processes it fully controls. (`rag-api` is not managed — you run it yourself; see §3.)
- It proxies `docs-search`'s and `doc-hierarchy`'s tools to Desktop under prefixed names (`docs-search__search`, etc.), decided once at startup.
- When you ask it to restart `docs-search`, it kills and respawns *its own child* and reconnects *its own internal client* — none of which Desktop needs to know about. From Desktop's point of view, the tool `docs-search__search` never disappeared; it just failed for a second and now works again.

### What this fixes vs. doesn't

| | Works without a full Desktop restart |
|---|---|
| `docs-search` crashed, restart it | ✅ |
| Picked up a code change to an *existing* tool's logic | ✅ |
| See status and start time of every managed server | ✅ |
| See recent logs for a server | ✅ |
| Child processes cleaned up when the client quits | ✅ — but only because of §2.2 |
| A **new** tool was added to `docs-search` that Desktop has never seen | ❌ — still needs a full Desktop restart, same as today |
| `mcp-manager` itself crashes | ❌ — same as any other MCP server today |

That's a fair trade for a hackathon: the annoying, high-frequency case (crash/hang/logic-change during iteration) gets fixed; the rare case (brand-new tool signature) doesn't regress, it just isn't improved.

## 2.1. Leak found during implementation: `npm run` on Windows

`command: "npm", args: ["run", "mcp", "-w", "docs-search"]` looks fine, but on Windows `npm` resolves to `npm.cmd`, so the real chain is `cmd.exe` → `node` (tsx CLI) → `node` (the actual server). `mcp-manager` only ever holds a handle to the outermost `cmd.exe`.

So `restartServer` leaks. Killing the wrapper leaves the real `node` underneath running — with its old code and its live Azure Search client — orphaned and invisible. Every restart during a dev session adds another one.

Two-part fix, both applied below:

1. **Cut the wrapper chain.** Spawn `node` directly with `--import tsx`, not `npm run` — one real process between `mcp-manager` and the server.
2. **Tree-kill as a backstop.** Don't assume nothing will ever fork a grandchild; `tree-kill` takes out the whole tree, not just the handle we hold.

## 2.2. Second leak: nothing shuts down when the client disconnects

Closing stdin — what an MCP client does when it quits — leaves `mcp-manager` *and* every child still running. Two causes stack up:

- **The SDK never tells us.** `StdioServerTransport.start()` registers `'data'` and `'error'` handlers on stdin and nothing else — no `'end'`, no `'close'`. A client disconnect never fires `server.onclose`, so a handler hung off it is dead code.
- **The process can't exit on its own anyway.** The children's stdio pipes keep `mcp-manager`'s event loop alive indefinitely.

So every client quit stranded `mcp-manager` plus one process per managed server, holding stale code.

Fix (§6.10): listen on `process.stdin` for `'end'`/`'close'` directly, plus `SIGINT`/`SIGTERM`, and `stopServer` every child — which tree-kills — before exiting. This is independent of how `mcp-manager` itself is launched; stdin EOF propagates fine through an `npx`/`cmd.exe` wrapper.

## 3. Architecture

```
Claude Desktop
     |  single stdio connection, tools/list fetched once at launch
     v
+-------------------+
|   mcp-manager      |   <-- the only entry in claude_desktop_config.json
|                     |
|  management tools:  |
|   - list_mcp_servers|
|   - restart_mcp_server
|   - get_mcp_server_logs
+-------------------+
   |  spawns + owns          |  spawns + owns
   |  (MCP client, proxied)  |  (MCP client, proxied)
   v                         v
docs-search               doc-hierarchy
(stdio child)              (stdio child)

rag-api runs separately (you start/stop it yourself) —
docs-search / doc-hierarchy just call it over HTTP.
```

Managed entries are declared in `servers.json` — each one a real MCP server that `mcp-manager` spawns, speaks MCP to over stdio via an internal client, and re-exposes with a `<name>__` tool prefix. That's what `docs-search` and `doc-hierarchy` are, and it's the only kind there is: an earlier draft carried a second `type: "process"` variant (spawn + supervise only, no proxying) for `rag-api`, but with `rag-api` out of scope that was an abstraction with no consumer. See §9 if you ever want it back.

## 4. Non-goals (hackathon scope)

- No auto-restart-on-crash / health checks — restart is user-triggered only, as asked.
- No remote/network transport, no auth — local dev, trusted single user.
- No dynamic `tools/list_changed` handling — see the "new tool" limitation above.
- No Windows-service / cross-machine process management.

### 6.2 No build step

Everything runs through `tsx`, same as `docs-search`, `doc-hierarchy` and `rag-api` — there is no `tsconfig.json` and no `build` script anywhere in this repo. A `tsc` → `dist/` setup would mean recompiling before every `mcp-manager` change, which is a poor trade for the one server you *can't* hot-restart from inside a chat.

The tradeoff: no compile-time gate. Two things `tsc --strict` would have caught, and which the code below already works around — keep them in mind if you ever do add a build:

- `MANAGEMENT_TOOLS` must be annotated `Tool[]`, otherwise `inputSchema.type: "object"` widens to `string` and stops satisfying `Tool`.
- Tool results need `type: "text" as const` for the same reason.

### 6.3 `mcp-manager/servers.json`

`cwd` is resolved relative to this file's own directory (see `config.ts`). Per §2.1, `command`/`args` deliberately spawn `node` directly with `--import tsx`, not `npm run` — that skips `cmd.exe`/`npm.cmd` entirely on Windows, so the pid `mcp-manager` gets back is the actual server process. `cwd` is each workspace's own folder so relative imports and `.env` loading behave exactly as they would under `npm run mcp -w <name>`, just without the shell hop.

```json
{
  "servers": {
    "docs-search": {
      "command": "node",
      "args": ["--import", "tsx", "src/mcpServer.ts"],
      "cwd": "../docs-search",
      "restartDelayMs": 500
    },
    "doc-hierarchy": {
      "command": "node",
      "args": ["--import", "tsx", "src/mcpServer.ts"],
      "cwd": "../doc-hierarchy",
      "restartDelayMs": 500
    }
  }
}
```

`src/mcpServer.ts` is the actual entrypoint filename in both packages — they have no `build` script and no `dist/`, so this points straight at source.

> **`--import tsx` only works because `cwd` is set.** `tsx` there is a *bare specifier*, and Node resolves it against the working directory, not the script's location. That's fine for children (we set `cwd` to the package folder), but it's why §7.3 does **not** use this form for `mcp-manager` itself — an MCP client launches it from its own working directory, where `tsx` doesn't resolve:
>
> ```
> Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'tsx' imported from C:\
> ```

`rag-api` is not listed here — start it yourself (`npm run rag-api` in its own terminal). `docs-search`/`doc-hierarchy` just need it reachable over HTTP; `mcp-manager` doesn't need to know it exists.

> **Note:** whatever command each of `docs-search` / `doc-hierarchy` runs must write **only** MCP JSON-RPC to stdout — no stray `console.log`. `mcp-manager` parses stdout line-by-line as MCP messages; any non-JSON line on stdout will break the connection. Send diagnostic output to stderr instead (that's what `logger.ts` captures for `get_mcp_server_logs`).

### 6.5 `mcp-manager/src/config.ts`

The registry path is a parameter, not a constant: `--config <path>` → `MCP_MANAGER_CONFIG` → the bundled `servers.json`. A CLI arg is the thing an MCP client can actually set per-entry in its own config file, so different clients can drive different sets of children off one install.

```typescript
import fs from "node:fs";
import path from "node:path";
import { fileURLToPath } from "node:url";
import type { ServersConfigFile } from "./types.js";

export const packageRoot = fileURLToPath(new URL("..", import.meta.url));

function suppliedConfigPath(): string | undefined {
  const argv = process.argv.slice(2);
  for (let i = 0; i < argv.length; i++) {
    if (argv[i] === "--config") return argv[i + 1];
    if (argv[i].startsWith("--config=")) return argv[i].slice("--config=".length);
  }
  return process.env.MCP_MANAGER_CONFIG;
}

const supplied = suppliedConfigPath();
export const CONFIG_PATH = supplied
  ? path.resolve(packageRoot, supplied)
  : path.join(packageRoot, "servers.json");
export const CONFIG_DIR = path.dirname(CONFIG_PATH);

export function loadServersConfig(): ServersConfigFile {
  const parsed = JSON.parse(fs.readFileSync(CONFIG_PATH, "utf-8")) as ServersConfigFile;
  if (!parsed.servers || Object.keys(parsed.servers).length === 0) {
    throw new Error(`No servers defined in ${CONFIG_PATH}`);
  }
  return parsed;
}

/** Relative to the config file's own directory — never process.cwd(), which is wherever
 *  the MCP client happened to launch mcp-manager from. */
export function resolveCwd(cwd: string | undefined): string {
  return path.resolve(CONFIG_DIR, cwd ?? ".");
}
```

Note `resolveCwd` anchors to the **config file's** directory, not `packageRoot` — a client-supplied registry lives wherever that client keeps it, and its relative `cwd` values should be read against itself.

### 6.6 `mcp-manager/src/logger.ts`

Per-server ring buffer (for `get_mcp_server_logs`) plus a flat file. The log directory is `hackathon/logs/` — **outside** the repo, matching where `doc-hierarchy` already writes its notifications (`002`), so logs survive branch switches and aren't caught by the `**/docs/**` ignore rules.

```typescript
import { appendFileSync, mkdirSync } from "node:fs";
import path from "node:path";
import { packageRoot } from "./config.js";

const LOG_DIR = process.env.MCP_MANAGER_LOG_DIR ?? path.resolve(packageRoot, "..", "..", "logs");
const LOG_FILE = path.join(LOG_DIR, "mcp-manager.log");

mkdirSync(LOG_DIR, { recursive: true });

const ringBuffers = new Map<string, string[]>();
const RING_SIZE = 200;

export function log(serverName: string, line: string): void {
  const entry = `[${new Date().toISOString()}] [${serverName}] ${line}`;

  const buf = ringBuffers.get(serverName) ?? [];
  buf.push(entry);
  if (buf.length > RING_SIZE) buf.shift();
  ringBuffers.set(serverName, buf);

  try {
    appendFileSync(LOG_FILE, entry + "\n");
  } catch {
    // Best-effort only — never let logging crash the manager.
  }
}

export function getRecentLogs(serverName: string, lines = 50): string[] {
  return (ringBuffers.get(serverName) ?? []).slice(-lines);
}
```

Anchored to `packageRoot`, not `CONFIG_DIR` — the log location shouldn't move just because someone passed `--config` pointing elsewhere.

### 6.7 `mcp-manager/src/childProcessTransport.ts`

A minimal MCP stdio client transport we own outright, so we always have the child's PID and full kill control (rather than relying on undocumented internals of the SDK's built-in `StdioClientTransport`). MCP stdio framing is one JSON-RPC message per line.

```typescript
import { spawn, type ChildProcessWithoutNullStreams } from "node:child_process";
import type { JSONRPCMessage } from "@modelcontextprotocol/sdk/types.js";

export interface ChildProcessTransportOptions {
  cwd: string;
  env?: Record<string, string>;
}

export class ChildProcessTransport {
  private child?: ChildProcessWithoutNullStreams;
  private buffer = "";

  onmessage?: (message: JSONRPCMessage) => void;
  onerror?: (error: Error) => void;
  onclose?: () => void;
  onStderr?: (text: string) => void;
  onExit?: (code: number | null) => void;

  constructor(
    private command: string,
    private args: string[],
    private options: ChildProcessTransportOptions
  ) {}

  get pid(): number | undefined {
    return this.child?.pid;
  }

  async start(): Promise<void> {
    const child = spawn(this.command, this.args, {
      cwd: this.options.cwd,
      env: { ...process.env, ...this.options.env },
      stdio: ["pipe", "pipe", "pipe"],
    });
    this.child = child;

    child.stdout.on("data", (chunk: Buffer) => this.handleChunk(chunk));
    child.stderr.on("data", (chunk: Buffer) => this.onStderr?.(chunk.toString()));
    child.on("error", (err) => this.onerror?.(err));
    child.on("exit", (code) => {
      this.onExit?.(code);
      this.onclose?.();
    });

    // Resolve only once the OS has actually started the process, so a bad command surfaces
    // here instead of as a silent hang waiting for an `initialize` response that never comes.
    await new Promise<void>((resolve, reject) => {
      child.once("spawn", resolve);
      child.once("error", reject);
    });
  }

  private handleChunk(chunk: Buffer): void {
    this.buffer += chunk.toString();
    let newlineIndex: number;
    while ((newlineIndex = this.buffer.indexOf("\n")) !== -1) {
      const line = this.buffer.slice(0, newlineIndex).trim();
      this.buffer = this.buffer.slice(newlineIndex + 1);
      if (!line) continue;
      try {
        this.onmessage?.(JSON.parse(line) as JSONRPCMessage);
      } catch {
        this.onerror?.(new Error(`Failed to parse message from child: ${line}`));
      }
    }
  }

  async send(message: JSONRPCMessage): Promise<void> {
    if (!this.child?.stdin.writable) {
      throw new Error("Child process is not running");
    }
    this.child.stdin.write(JSON.stringify(message) + "\n");
  }

  async close(): Promise<void> {
    if (this.child && !this.child.killed) {
      this.child.kill();
    }
  }
}
```

`onExit` is separate from `onclose` on purpose: the SDK's `Protocol.connect()` chains onto `onclose`, so §6.8 needs its own untouched hook to detect a child dying *during* the handshake.

The class satisfies the SDK's `Transport` interface structurally — that interface requires only `start`, `send`, `close`; `onclose`/`onerror`/`onmessage`/`sessionId`/`setProtocolVersion` are all optional.

### 6.8 `mcp-manager/src/processManager.ts`

Owns the lifecycle (start/stop/restart) for every managed server.

```typescript
import treeKill from "tree-kill";
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { ChildProcessTransport } from "./childProcessTransport.js";
import { resolveCwd } from "./config.js";
import { log, getRecentLogs } from "./logger.js";
import type { ManagedServerConfig, ManagedServerInfo, ServerStatus } from "./types.js";

function killTree(pid: number): Promise<void> {
  return new Promise((resolve) => {
    treeKill(pid, "SIGTERM", (err) => {
      // A missing/already-dead pid is not a failure worth surfacing.
      if (err) log("mcp-manager", `tree-kill on pid ${pid}: ${err.message}`);
      resolve();
    });
  });
}

interface ManagedServer {
  transport: ChildProcessTransport;
  client: Client;
}

const servers = new Map<string, ManagedServer>();
const statuses = new Map<string, ServerStatus>();
const restartCounts = new Map<string, number>();
const lastErrors = new Map<string, string>();
const startedAt = new Map<string, string>();

export async function startServer(name: string, config: ManagedServerConfig): Promise<void> {
  statuses.set(name, "starting");
  lastErrors.delete(name);

  const transport = new ChildProcessTransport(config.command, config.args, {
    cwd: resolveCwd(config.cwd),
    env: config.env,
  });
  transport.onStderr = (text) => {
    for (const line of text.split("\n")) if (line.trim()) log(name, line.trim());
  };
  transport.onerror = (err) => {
    lastErrors.set(name, err.message);
    log(name, `ERROR: ${err.message}`);
  };
  transport.onclose = () => {
    // A child that exits on its own lands here too, not just a deliberate stop.
    if (statuses.get(name) === "running") {
      statuses.set(name, "crashed");
      log(name, "process exited unexpectedly");
    }
  };

  // Without this, a child that spawns fine but dies before answering `initialize` leaves
  // client.connect() waiting on the SDK's 60s request timeout.
  let connected = false;
  const diedDuringHandshake = new Promise<never>((_, reject) => {
    transport.onExit = (code) => {
      if (!connected) reject(new Error(`exited (code ${code}) before completing MCP initialize`));
    };
  });

  const client = new Client({ name: `mcp-manager-proxy-${name}`, version: "1.0.0" });

  try {
    await Promise.race([client.connect(transport), diedDuringHandshake]);
    connected = true;
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    statuses.set(name, "crashed");
    lastErrors.set(name, message);
    log(name, `failed to start: ${message}`);
    if (transport.pid) await killTree(transport.pid);
    throw err;
  }

  servers.set(name, { transport, client });
  statuses.set(name, "running");
  startedAt.set(name, new Date().toISOString());
  log(name, `started (pid ${transport.pid})`);
}

export async function stopServer(name: string): Promise<void> {
  const server = servers.get(name);
  if (!server) return;

  const pid = server.transport.pid;
  try {
    await server.client.close();
  } catch (err) {
    log(name, `client.close() during stop: ${(err as Error).message}`);
  }

  // Kill the whole tree under this pid, not just the handle we spawned. The `node --import tsx`
  // spawn path normally has nothing underneath, but this is what prevents orphans if that
  // changes (a dependency that forks, or someone reverting to an `npm run` command).
  if (pid) await killTree(pid);

  servers.delete(name);
}

export async function restartServer(name: string, config: ManagedServerConfig): Promise<void> {
  statuses.set(name, "restarting");
  log(name, "restart requested");
  await stopServer(name);

  await new Promise((resolve) => setTimeout(resolve, config.restartDelayMs ?? 500));
  restartCounts.set(name, (restartCounts.get(name) ?? 0) + 1);

  try {
    await startServer(name, config);
  } catch {
    // startServer already recorded status and lastError; a failed restart shouldn't
    // propagate as a tool-call exception.
  }
}

export function getClient(name: string): Client | undefined {
  return servers.get(name)?.client;
}

export function getServerInfo(name: string): ManagedServerInfo {
  return {
    name,
    status: statuses.get(name) ?? "stopped",
    pid: servers.get(name)?.transport.pid,
    startedAt: startedAt.get(name),
    restartCount: restartCounts.get(name) ?? 0,
    lastError: lastErrors.get(name),
  };
}

export { getRecentLogs };
```

`restarting` matters more than it looks: without it, a `list_mcp_servers` call landing mid-restart reports `stopped`, which reads like a failure. MCP requests are handled concurrently, so this is easy to hit.

### 6.9 `mcp-manager/src/toolProxy.ts`

```typescript
import type { Tool } from "@modelcontextprotocol/sdk/types.js";
import { getClient } from "./processManager.js";
import { log } from "./logger.js";

interface ProxiedTool {
  serverName: string;
  originalName: string;
  tool: Tool; // name already rewritten to `${serverName}__${originalName}`
}

const proxiedTools = new Map<string, ProxiedTool>();

export async function refreshProxiedTools(serverNames: string[]): Promise<void> {
  for (const name of serverNames) {
    const client = getClient(name);
    if (!client) continue;

    try {
      const { tools } = await client.listTools();
      // Drop this server's previous entries first, so a tool removed from the child's source
      // doesn't linger in the proxy after a restart.
      for (const [key, proxied] of proxiedTools) {
        if (proxied.serverName === name) proxiedTools.delete(key);
      }
      for (const tool of tools) {
        const prefixedName = `${name}__${tool.name}`;
        proxiedTools.set(prefixedName, {
          serverName: name,
          originalName: tool.name,
          tool: { ...tool, name: prefixedName, description: `[${name}] ${tool.description ?? ""}` },
        });
      }
      log(name, `discovered ${tools.length} tool(s)`);
    } catch (err) {
      log(name, `failed to list tools: ${(err as Error).message}`);
    }
  }
}

export function getProxiedToolDefinitions(): Tool[] {
  return [...proxiedTools.values()].map((p) => p.tool);
}

export async function callProxiedTool(prefixedName: string, args: unknown) {
  const proxied = proxiedTools.get(prefixedName);
  if (!proxied) throw new Error(`Unknown tool: ${prefixedName}`);

  const client = getClient(proxied.serverName);
  if (!client) {
    throw new Error(`"${proxied.serverName}" is not running — use restart_mcp_server first.`);
  }

  return client.callTool({ name: proxied.originalName, arguments: args as Record<string, unknown> });
}
```

```typescript
  {
    name: "get_mcp_server_logs",
    description: "Return recent stderr output captured from a managed server (for debugging a crash).",
    inputSchema: {
      type: "object",
      properties: {
        name: { type: "string", description: "Server name as it appears in list_mcp_servers." },
        lines: { type: "number", description: "Number of lines to return (default 50)." },
      },
      required: ["name"],
    },
  },
];

const text = (value: string) => ({ content: [{ type: "text" as const, text: value }] });

async function main(): Promise<void> {
  const { servers: serverConfigs } = loadServersConfig();
  const serverNames = Object.keys(serverConfigs);

  const server = new Server(
    { name: "mcp-manager", version: "1.0.0" },
    { capabilities: { tools: {} } }
  );

  server.setRequestHandler(ListToolsRequestSchema, async () => ({
    tools: [...MANAGEMENT_TOOLS, ...getProxiedToolDefinitions()],
  }));

  server.setRequestHandler(CallToolRequestSchema, async (req) => {
    const { name, arguments: args } = req.params;

    switch (name) {
      case "list_mcp_servers":
        return text(JSON.stringify(serverNames.map(getServerInfo), null, 2));

      case "restart_mcp_server": {
        const { name: target } = z.object({ name: z.string() }).parse(args);
        const config = serverConfigs[target];
        if (!config) {
          return {
            ...text(`Unknown server "${target}". Known servers: ${serverNames.join(", ")}`),
            isError: true,
          };
        }
        await restartServer(target, config);
        await refreshProxiedTools([target]);
        return text(JSON.stringify(getServerInfo(target), null, 2));
      }

      case "get_mcp_server_logs": {
        const parsed = z.object({ name: z.string(), lines: z.number().optional() }).parse(args);
        return text(getRecentLogs(parsed.name, parsed.lines ?? 50).join("\n") || "(no logs yet)");
      }

      default:
        try {
          return await callProxiedTool(name, args);
        } catch (err) {
          return { ...text(`Error calling ${name}: ${(err as Error).message}`), isError: true };
        }
    }
  });

  // Boot every managed server before talking to the client, so the very first tools/list
  // response already includes the proxied tools.
  for (const serverName of serverNames) {
    try {
      await startServer(serverName, serverConfigs[serverName]);
    } catch {
      // startServer already logged it and marked the server crashed; one bad child must not
      // stop mcp-manager itself from coming up.
    }
  }
  await refreshProxiedTools(serverNames);

  await server.connect(new StdioServerTransport());

  // Nothing tears the children down for us. The SDK's StdioServerTransport only listens for
  // stdin 'data'/'error', so a client disconnect never fires server.onclose — and the
  // children's open pipes keep this event loop alive, leaking every process on client quit.
  let shuttingDown = false;
  const shutdown = async () => {
    if (shuttingDown) return;
    shuttingDown = true;
    log("mcp-manager", "client disconnected, stopping managed servers");
    await Promise.all(serverNames.map(stopServer));
    process.exit(0);
  };

  process.stdin.on("end", () => void shutdown());
  process.stdin.on("close", () => void shutdown());
  process.on("SIGINT", () => void shutdown());
  process.on("SIGTERM", () => void shutdown());

  log("mcp-manager", `connected to client, managing: ${serverNames.join(", ")}`);
}

main().catch((err) => {
  console.error("mcp-manager fatal error:", err);
  process.exit(1);
});
```

The stdin listeners are attached **after** `server.connect(...)` on purpose — the transport's own `'data'` listener is what puts stdin into flowing mode, and `'end'` won't fire on a paused stream.

`restart_mcp_server` returns the server's full info record rather than `"Restarted X"`, so a failed restart is visible (`status: "crashed"` plus `lastError`) instead of reporting success.

### 7.1 Root `package.json`


Optional convenience script:


### 7.2 Install

```bash
cd mcp-rag-hackathon
npm install
```

That's it — no build step (§6.2). `tsx` and `@types/node` are already dev dependencies at the workspace root.

### 7.3 `claude_desktop_config.json`

Locations:
- macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`
- Windows: `%APPDATA%\Claude\claude_desktop_config.json` (or under `AppData\Local\Packages\Claude_*\LocalCache\Roaming\Claude\` for the Store build)

Replace whatever entries you currently have for `docs-search` / `doc-hierarchy` with a single one:

```json
{
  "mcpServers": {
    "mcp-manager": {
      "command": "npx",
      "args": [
        "tsx",
        "C:\\absolute\\path\\mcp-rag-hackathon\\mcp-manager\\src\\mcpServer.ts",
        "--config",
        "C:\\absolute\\path\\mcp-rag-hackathon\\mcp-manager\\servers.json"
      ]
    }
  }
}
```

Use absolute paths — the client doesn't launch this with your shell's `PATH` or working directory.

**Why `npx tsx` here but `node --import tsx` in §6.3.** The children get a `cwd` we control, so a bare `tsx` specifier resolves. `mcp-manager` itself doesn't — the client launches it from its own directory, where `--import tsx` fails outright (§6.3). `npx` resolves regardless of cwd. The extra `cmd.exe` hop costs nothing here: this process's lifetime is the client's business, not ours, and stdin EOF still propagates through the wrapper, so §2.2's shutdown path works either way.

If you *do* want a wrapper-free launch, the only form Node accepts is an absolute **file URL** to the loader — a plain Windows path is parsed as a URL scheme and rejected with `ERR_UNSUPPORTED_ESM_URL_SCHEME: Received protocol 'c:'`:

```json
"args": ["--import", "file:///C:/absolute/path/node_modules/tsx/dist/loader.mjs", "..."]
```

**This one edit still needs a full client restart** (that's unavoidable — it's how any MCP server is first registered). After that, restarting `docs-search`/`doc-hierarchy` individually never requires another one.

## 8. Trying it out

1. Fully quit and reopen Claude Desktop once, after step 7.3.
2. In a chat: *"What MCP servers are you tracking?"* → should call `list_mcp_servers` and return both servers as `running`.
3. Edit any file under `docs-search/src/`. There's nothing to rebuild — it runs through `tsx`.
4. In the same chat: *"Restart docs-search"* → calls `restart_mcp_server({ name: "docs-search" })`. The manager refreshes the proxy and emits `notifications/tools/list_changed`, so clients that honor the notification see added or removed tools without reconnecting. Claude Desktop versions that ignore it still require a full Desktop restart when the tool set changes; implementation-only edits do not.
5. If something looks off: *"Show me the last 50 log lines for doc-hierarchy"* → calls `get_mcp_server_logs`.
6. **Check the two leaks from §2.1 and §2.2 once**, right after wiring this up. Count `mcp-manager`'s child processes (`Get-CimInstance Win32_Process -Filter "ParentProcessId=<mgrPid>"` on Windows, `pgrep -P <mgrPid>` elsewhere):
   - after a restart, the count should be unchanged — if it climbs by one each time, tree-kill isn't reaching the real process;
   - after quitting the client, `mcp-manager` and all of its children should be gone.

   Match on **parent pid**, not command-line text. `pgrep -fl docs-search` and friends match nothing here — §6.3 launches `node --import tsx src/mcpServer.ts` with the package name only in `cwd` — so you get "0 before, 0 after" and read it as a pass.
