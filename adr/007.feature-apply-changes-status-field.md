# 007 — `apply_change`: reset approval metadata on edit

**Scope:** `doc-hierarchy` only. Addendum to `005.feature-apply-changes.md` — same file,
same function, one more thing it does per call.
**Relates to:** `005.feature-apply-changes.md` (`applyChange.ts`, `mcpServer.ts`'s `apply_change`
tool).

**The problem:** `apply_change` edits a paragraph but never touches the metadata table's
`Status` or `Signoff Date` fields. A document that was `Approved (Baseline X)` stays marked
approved with its previous signoff date even after a tracked change lands in it — misleading,
since that approval and signoff no longer reflect the document's current content the moment an
edit is proposed.

**The fix:** the moment `apply_change` runs, if `Status` currently reads exactly
`Approved (Baseline N)` where `N` is the *current* latest baseline's number, flip it to
`Draft` and reset `Signoff Date` to `TBD`. Values in play, per confirmation:
`Draft` | `Approved (Baseline X)`.

---

## Key design decisions (and why)

- **These are tracked changes.** The Status and Signoff Date replacements use native Word
  `<w:del>`/`<w:ins>` revisions, authored by the document owner with the same timestamp as the
  paragraph proposal. A reviewer can therefore accept or reject the content and metadata
  proposals in Word.
- **Gated on the approval matching the *current* latest baseline specifically**, not just "any
  `Approved (...)` value." An approval against an older, already-superseded baseline is a
  different, already-stale situation this doesn't try to touch — only flip when the approval
  literally refers to the same baseline this draft is currently building on top of.
- **Naturally idempotent, no special-casing needed.** A second `apply_change` call against the
  same document (the "revise the pending proposal" path from `005`) finds `Status` already
  reading `Draft` and `Signoff Date` already reading `TBD` from the first call — the regex no
  longer matches, so nothing happens the second time. This falls out of the design rather than
  needing an explicit check.
- **Same load-mutate-write cycle as the paragraph edit — one file write.** The Status check and
  both metadata updates happen on the same in-memory DOM, right before the existing
  serialize-and-save step.

## `doc-hierarchy/src/applyChange.ts` — additions

Two new helper functions, added alongside the existing ones:

```ts
const APPROVED_BASELINE_STATUS = /^Approved \(Baseline (\d+)\)$/;

function replaceCellTextAsTrackedChange(
  doc: Document, cell: Node, newText: string, author: string, date: string
) {
  const oldText = (select(".//w:t", cell) as Node[]).map(n => n.textContent ?? "").join("");
  (select(".//w:r", cell) as Node[]).forEach(r => r.parentNode?.removeChild(r));
  const paragraph = (select(".//w:p", cell) as Node[])[0];
  const delId = nextRevisionId(doc);
  const delNode = parseFragment(
    `<w:del xmlns:w="${W_NS}" w:id="${delId}" w:author="${xmlEscape(author)}" w:date="${date}">` +
    `<w:r><w:delText xml:space="preserve">${xmlEscape(oldText)}</w:delText></w:r></w:del>`
  );
  const insNode = parseFragment(
    `<w:ins xmlns:w="${W_NS}" w:id="${delId + 1}" w:author="${xmlEscape(author)}" w:date="${date}">` +
    `<w:r><w:t xml:space="preserve">${xmlEscape(newText)}</w:t></w:r></w:ins>`
  );
  paragraph.appendChild(doc.importNode(delNode, true));
  paragraph.appendChild(doc.importNode(insNode, true));
}

/** Flips Status from "Approved (Baseline N)" to "Draft", but only when N matches
 *  the current latest baseline — an approval against an older baseline is a
 *  different (already stale) situation this doesn't touch. */
function updateStatusIfApproved(
  doc: Document, latestBaselineName: string, author: string, date: string
): boolean {
  const latestNumber = latestBaselineName.match(/-(\d+)$/)?.[1];
  if (!latestNumber) return false;

  const rows = select("//w:tbl/w:tr", doc) as Node[];
  for (const row of rows) {
    const cells = select("./w:tc", row) as Node[];
    if (cells.length < 2) continue;

    const label = (select(".//w:t", cells[0]) as Node[]).map(n => n.textContent ?? "").join("").trim();
    if (label !== "Status") continue;

    const value = (select(".//w:t", cells[1]) as Node[]).map(n => n.textContent ?? "").join("").trim();
    const match = value.match(APPROVED_BASELINE_STATUS);
    if (match && match[1] === latestNumber) {
      replaceCellTextAsTrackedChange(doc, cells[1], "Draft", author, date);
      for (const signoffRow of rows) {
        const signoffCells = select("./w:tc", signoffRow) as Node[];
        if (signoffCells.length < 2) continue;

        const signoffLabel = (select(".//w:t", signoffCells[0]) as Node[])
          .map(n => n.textContent ?? "").join("").trim();
        if (signoffLabel === "Signoff Date") {
          replaceCellTextAsTrackedChange(doc, signoffCells[1], "TBD", author, date);
          break;
        }
      }
      return true;
    }
    return false; // found Status, condition didn't hold — nothing to do
  }
  return false; // no Status row at all
}
```

## Test addition

Automated tests use disposable DOCX fixtures. After running `apply_change` against a document
whose Status is `Approved (Baseline <latest>)`, confirm both metadata cells contain native Word
tracked revisions: the old Status and Signoff Date in `<w:del>/<w:delText>`, and `Draft` and
`TBD` in `<w:ins>/<w:t>`, all attributed to the document owner. The negative check uses
`Approved (Baseline N)` where `N` is not the latest baseline and confirms both fields remain
untracked and untouched. A repeat-edit check confirms no duplicate metadata revisions are added.
