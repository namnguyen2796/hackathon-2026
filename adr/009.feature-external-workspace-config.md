# 009 — externally-configured workspace and log paths

**Scope:** `doc-hierarchy` and `docs-search` both.
**Relates to:** the updated `008` (`baselines.ts`, `signoffStore.ts`, `notify_owner`'s log path),
`006` (`mcp-manager` — this relies on its existing `servers.json` `env` field, §6.4/6.7 of that
doc; the only change there is untracking `servers.json` and a first-run guard),
`000.hackathon-setup.md`'s `.gitignore`.

**Revision note:** the first draft of this doc opened with a question about whether
`mcp-manager` spawns sub-servers as child processes at all, since that wasn't written down
anywhere yet. `006` (pasted since) confirms it does, and — better — that per-server environment
variables are already a first-class, already-implemented part of its config format. This
version replaces the "here's a contract mcp-manager needs to implement" framing with "here's
how to use what's already there."

**The problem:** `docs/` (and, via `008`, `logs/`) live inside the repo, gitignored to keep
sample/operational data out of version control. That only half-works — the folders still exist
in the repo, and nothing stops code from defaulting back into them.

**The fix:** `doc-hierarchy` and `docs-search` read their data location from environment
variables. Those variables are set per-server in `mcp-manager/servers.json`'s existing `env`
field — no new mechanism, just populating a field that was already there for exactly this kind
of thing.

---

## Where the values actually get set

`006`'s `servers.json` schema (`ManagedServerConfig`) already has this shape:
```ts
export interface ManagedServerConfig {
  command: string;
  args: string[];
  cwd?: string;
  env?: Record<string, string>;   // <- already here
  restartDelayMs?: number;
}
```
and `processManager.ts` already passes it through to the child, layered over inherited
environment (`childProcessTransport.ts`: `env: { ...process.env, ...this.options.env }`).

So the mechanism is entirely in place. The only thing that changes in `mcp-manager` is **which
side of the git boundary `servers.json` sits on.**

### `servers.json` leaves the repo; `servers.example.json` is what ships

`servers.json` was committed. The moment it holds a real workspace path it also holds one
developer's machine layout, pushed to everyone's checkout — the same leak this whole change
exists to close, just relocated. But the file is *also* the only sensible home for those paths:
it already keys configuration by server name, which is exactly the grouping needed.

Both are satisfied by deleting it from the repo and shipping a template beside it:

- `mcp-manager/servers.example.json` — **tracked.** Real structure, obviously-fake paths. This
  is the file that documents what an operator is expected to supply.
- The operator's own copy — **not in the repo at all.** Keep it wherever machine-local config
  lives and point `--config` at it; `006` built that flag for exactly this. Copying it to
  `mcp-manager/servers.json` also works, since that's still the default lookup.

No ignore rule is involved. An ignore rule would only be needed to hide a file the repo is
expected to contain, and it isn't — the repo's copy is gone.

```json
{
  "servers": {
    "docs-search": {
      "command": "node",
      "args": ["--import", "tsx", "src/mcpServer.ts"],
      "cwd": "../docs-search",
      "restartDelayMs": 500,
      "env": {
        "MCP_CONFIG_WORKSPACE": "C:\\absolute\\path\\to\\docs (docs-search)"
      }
    },
    "doc-hierarchy": {
      "command": "node",
      "args": ["--import", "tsx", "src/mcpServer.ts"],
      "cwd": "../doc-hierarchy",
      "restartDelayMs": 500,
      "env": {
        "MCP_CONFIG_WORKSPACE": "C:\\absolute\\path\\to\\docs (doc-hierarchy)",
        "MCP_CONFIG_LOGSPACE": "C:\\absolute\\path\\to\\logs"
      }
    }
  }
}
```

**No placeholder-substitution layer, and nothing added to the MCP client config.** Both were
tempting — `${VAR}` references in a tracked `servers.json`, expanded from variables set on
`mcp-manager`'s own entry in `claude_desktop_config.json`. Both are strictly worse than moving
the file out: they keep machine-specific values *somewhere*, just split across two files, and
they require inventing a second set of variable names (`DOC_HIERARCHY_WORKSPACE` →
`MCP_CONFIG_WORKSPACE`) whose only purpose is to survive the hop. An environment block also
can't express the per-server grouping at all — a process environment is a flat `string → string`
map — so the nesting would have to be flattened by hand into uniquely-prefixed names. One file
that already nests correctly, kept outside the repo, is less machinery and a better shape.

If the copy lives at the default location, `cwd` values stay relative (`"../docs-search"`) and
keep working: `resolveCwd` anchors to `CONFIG_DIR`. A copy kept elsewhere needs absolute `cwd`
values, or relative ones written against its own directory.

### `loadServersConfig` gains a first-run error

A fresh clone now has no `servers.json`, and the bare `ENOENT` from `readFileSync` wouldn't say
why or what to do:

```ts
if (!fs.existsSync(CONFIG_PATH)) {
  throw new Error(
    `${CONFIG_PATH} not found. It holds machine-specific paths, so it is not shipped — copy ` +
    "mcp-manager/servers.example.json and fill it in, then place it here or pass --config."
  );
}
```
**Operational caveat worth knowing before relying on this:** `mcpServer.ts`'s `main()` calls
`loadServersConfig()` once, at `mcp-manager`'s own startup, and holds the result in memory for
its whole lifetime. Editing `servers.json` and then calling `restart_mcp_server` on the affected
child reuses the *already-loaded* config from before your edit — it won't pick up the change.
Picking up a `servers.json` edit needs `mcp-manager` itself restarted, which (per `006` §2)
means a full Claude Desktop restart, not just a managed-server restart. Worth knowing so a
changed workspace path doesn't look like it silently failed to apply.

## Key design decisions (and why)

- **No fallback to a repo-relative path if the variable isn't set — fail fast instead.** The
  entire point is that nothing can silently default back into the repo. A missing
  `MCP_CONFIG_WORKSPACE` throws immediately, naming exactly what's missing and where it needs to
  be configured.
- **The configured `workspace` path *is* the folder that directly contains `baseline-<N>`/
  `draft-<N>`** — not a parent folder with its own `docs/` subfolder inside it. The old
  `packageRoot/docs/baseline-N` had two roots worth naming only because `docs/` needed a
  `.gitignore` entry distinct from the rest of the package. Once it's fully external, that
  distinction serves no purpose.
- **`packageRoot` is retired from `baselines.ts`, and from every module that imported it from
  there.** Its only jobs were anchoring `docs/` and anchoring `logs/`, both of which now belong
  to `config.ts` — nothing left in the package needs a package-relative anchor. Three modules
  import it today: `ingest.ts`, `signoffStore.ts`, and `approve.ts`. The last one is the easiest
  to miss, because it doesn't just read paths — it *writes* to them, building both the promotion
  target and the new draft folder out of `path.join(packageRoot, "docs", …)`. Left alone,
  `approve_baseline` would rename a draft out of the external workspace and into the repo.
- **Path roots live in their own `config.ts`, not in whichever module first needed one.**
  `workspaceRoot()`/`logspaceRoot()` answer "where did the operator point this install," which
  is a different layer from `baselines.ts` (domain vocabulary: what a baseline is) and
  `signoffStore.ts` (one feature's persistence). Hanging them off those modules would make
  unrelated code import a domain or feature module to reach a config value — `signoffStore.ts`
  importing `baselines.js` for exactly that reason is the shape to avoid.
- **A document's indexed `source` field is relative to `workspaceRoot()`, not `packageRoot`.**
  Not optional — once files live outside the package entirely, "relative to the package
  directory" produces a nonsensical `../../../Users/...` path.
- **`.env` becomes an optional local-development convenience, not a second config path.**
  `dotenv`'s `config()` never overrides a variable already present in `process.env`. Since
  `mcp-manager` sets `MCP_CONFIG_WORKSPACE`/`MCP_CONFIG_LOGSPACE` on the child *before* any of
  that child's own module code runs, a matching `.env` entry is silently ignored in normal
  operation — the real, `servers.json`-provided value always wins. Running
  `node --import tsx src/mcpServer.ts` directly, bypassing `mcp-manager` entirely (for local
  testing), has no spawner to inject anything — for that case only, `.env` can supply the same
  variables. `createIndex.ts`/`ingest.ts` already call `dotenv`'s `config()` for Azure
  credentials; `mcpServer.ts` in both projects gets that same call added, since it currently has
  none — with `quiet: true`, which the scripts don't need but the servers do. `dotenv@17` prints
  `◇ injected env (n) from .env …` through `console.log`, i.e. onto **stdout**, which for an MCP
  server is the JSON-RPC stream (`006`'s "no stray `console.log`" note). Without `quiet`, adding
  the `.env` load would break the connection of any server started outside `mcp-manager`.
- **Anything reading `MCP_CONFIG_WORKSPACE`/`MCP_CONFIG_LOGSPACE` resolves it per call, never
  at module scope.** Two reasons, one per project type. In the long-lived MCP servers, a
  module-scope read means the fail-fast `throw` fires during import and takes down *every* tool,
  including the ones that never touch the missing folder; deferring it to call time fails only
  the tool that actually needed it, with a message the caller can see. In the tests, a cached
  module-scope path would freeze whichever temp directory happened to be current the first time
  the module loaded. The one exception is `docs-search/src/ingest.ts`, which is a top-to-bottom
  script with no tools to isolate — there, failing at load *is* failing fast.
- **`SIGNOFF_LOG_DIR` and `NOTIFY_LOG_DIR` (the test-only overrides `008` introduced) are
  retired in favor of the one `MCP_CONFIG_LOGSPACE`.** Production already configures "where do
  logs live" through an environment variable now — tests should set the same one, not a
  parallel test-only name.
- **`mcp-manager`'s own log directory is left exactly as `006` built it.** An earlier pass added
  a `--log-dir` CLI arg for it; that was solving nothing. `LOG_DIR`'s default,
  `packageRoot/../../logs`, already resolves outside the repo, and `006` already provided
  `MCP_MANAGER_LOG_DIR` for the rare case where it needs to move. Note this log is
  `mcp-manager`'s *own* operational record (`mcp-manager.log`) and has nothing to do with
  `MCP_CONFIG_LOGSPACE`, which is `doc-hierarchy`'s notification/signoff store — they've only
  ever shared a folder by coincidence.

## `doc-hierarchy/src/config.ts` — new

Both path roots are **configuration**, so they get their own module rather than being bolted
onto whichever file happened to need one first. `baselines.ts` is domain vocabulary — what a
baseline is, what the current draft is — and `signoffStore.ts` is one feature's persistence.
Neither is the right owner for "where did the operator point this install." Putting
`workspaceRoot()` in `baselines.ts` would also have forced `signoffStore.ts` to import
`baselines.js` purely to reach a config value, which is the wrong dependency direction and is
exactly the import the old code had.

```ts
function required(name: string): string {
  const value = process.env[name];
  if (!value) {
    throw new Error(
      `${name} is not set — add it to "doc-hierarchy"'s "env" in mcp-manager/servers.json, ` +
      "or export it directly when running a script or test by hand."
    );
  }
  return value;
}

/** The folder that directly contains baseline-<N>/draft-<N>. Lives outside the repo; there is
 *  deliberately no repo-relative fallback. Read per call so tests can redirect it. */
export function workspaceRoot(): string {
  return required("MCP_CONFIG_WORKSPACE");
}

/** Where operational records (signoffs, notifications) live. Same rules as workspaceRoot. */
export function logspaceRoot(): string {
  return required("MCP_CONFIG_LOGSPACE");
}
```

The two roots share a `required` helper because the failure is identical in both cases and the
message differs only by variable name. Consumers import from here directly rather than through
an intermediate re-export: `baselines.ts` and `approve.ts` and `ingest.ts` take `workspaceRoot`,
`signoffStore.ts` and `mcpServer.ts` take `logspaceRoot`.

## `doc-hierarchy/src/baselines.ts`

```diff
+import { workspaceRoot } from "./config.js";
```

Every existing function that currently derives a path from `packageRoot` + `"docs"` switches to
deriving it from `workspaceRoot()` — the internal logic of `latestBaselineNumber`,
`getLatestBaselineDir`, `getCurrentDraftDir`, `listDocxFiles`, `draftFilePath`, and
`resolveDocPath` doesn't otherwise change, only what they're anchored to. `resolveDocPath` is
the one worth reading twice: it previously resolved relative input against `packageRoot` and
*then* range-checked against `docsRoot`, two different anchors. Now both are the same
`workspaceRoot()`, and its error message says "escapes the workspace" rather than naming
`docs/`.

`packageRoot` is removed from this file — nothing left in it needs a package-relative anchor.

The other `packageRoot` consumer, and the only one that writes. Both halves of the promotion —

## Migration checklist

1. **Pick real locations, outside the repo, for each workspace and (for `doc-hierarchy`) log
   directory**, and move the existing sample data there. The repo's own parent directory is the
   obvious choice — it's already outside the repo, and `<parent>/logs/` is already where both
   `notify_owner` and `mcp-manager` have been writing all along:
   ```
   <parent>/docs (doc-hierarchy)/   <- MCP_CONFIG_WORKSPACE for doc-hierarchy
   <parent>/docs (docs-search)/     <- MCP_CONFIG_WORKSPACE for docs-search
   <parent>/logs/                   <- MCP_CONFIG_LOGSPACE for doc-hierarchy
   <parent>/<repo>/                 <- the repo itself
   ```
2. **Delete the in-repo `docs/` folders outright**, `.gitkeep` placeholders included. Their
   content is now duplicated at the locations from step 1, so diff the two before pulling the
   trigger — the in-repo copies are gitignored, meaning `git status` stays clean whatever state
   they're in and there is nothing to restore them from:
   ```bash
   git rm -r doc-hierarchy/docs docs-search/docs
   ```
3. **Delete `mcp-manager/servers.json` from the repo** and keep your own copy outside it
   (`--config`), or at the default path, seeded from `servers.example.json`:
   ```bash
   git rm mcp-manager/servers.json
   ```
4. **Fill in the three paths from step 1** under the matching server's `env` in your copy, then
   fully restart Claude Desktop once — per the operational caveat above, a managed-server-only
   restart won't pick up a `servers.json` edit. Forget the file entirely and
   `loadServersConfig` says which template to copy.
5. **Nothing to do for `mcp-manager`'s own log.** `LOG_DIR`'s default
   (`packageRoot/../../logs`) already resolves to `<parent>/logs/`, outside the repo, and `006`'s
   `MCP_MANAGER_LOG_DIR` is still there for the case where it has to move.
6. **Set the variables for local manual runs too**, either exported directly or via the
   monorepo-root `.env` (see the design decision above on why the latter is safe). These are the
   same two variables `servers.json` hands the child — running a script by hand just has no
   spawner to inject them:
   ```bash
   export MCP_CONFIG_WORKSPACE="/absolute/path/to/docs (doc-hierarchy)"
   export MCP_CONFIG_LOGSPACE="/absolute/path/to/logs"
   npm run doc-hierarchy:ingest
   ```
   `doc-hierarchy`'s suite needs neither: `signoff.test.ts` and `applyChange.test.ts` set
   `MCP_CONFIG_LOGSPACE` to their own temp directory before importing anything, and
   `approve.test.ts` only exercises `assertPromotable`, which takes an explicit `draftDir` and
   never consults the workspace.

## Remaining open items

- **Does `docs-search` ever need a `logspace`** of its own, or does the example config
  (workspace only) reflect a real, permanent difference between the two projects? Assumed the
  latter here.
- **`servers.example.json` can drift from a real `servers.json`** with nothing to catch it.
  Adding a server, or a new variable to an existing one, means remembering to update a file that
  no longer affects your own machine. Nothing validates the two against each other.
- **A copy placed at the default path is untracked but not ignored**, so it shows up in
  `git status` and can be committed by a careless `git add -A` — reintroducing exactly the leak
  this removed. Keeping the copy outside the repo and pointing `--config` at it avoids the
  question entirely.
- **Nothing validates that a configured workspace actually contains a `baseline-<N>`** until the
  first tool call that needs one, which then fails with `No baseline-<N> folders found under …`.
  That's the intended failure and the message names the offending path, but a typo'd path and a
  genuinely empty workspace are indistinguishable from it.
