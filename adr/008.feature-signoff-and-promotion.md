# 008 — signoff (owner + reviewer) and baseline promotion

**Scope:** `doc-hierarchy` only.
**Relates to:** `004` (`baselines.ts` — folder resolution), `005` (`applyChange.ts`, native tracked
changes).
**Supersedes:** `007`. That addendum made `apply_change` write its `Status`/`Signoff Date` reset as
tracked revisions, gated on the approval naming the current latest baseline. Both parts are
replaced here — see "Status field" below.
**Not covered:** any real login/identity system. Names are pulled from conversation context for
now (the calling agent extracts "M. Osei" from what the person said and passes it as a parameter).
A UI that actually knows who's logged in is future work.

**The three things this adds:**
1. `signoff` — owner and reviewer each approve a document; both are required.
2. Once both approvals land, `Status` becomes `Approved (Baseline N)` with a `Signoff Date`.
3. `approve_baseline` — once every document in the draft is `Approved`, promote the whole draft
   to a baseline and reindex.

---

## Folder and numbering model

**The latest baseline number is the only number in the system.** There is no such thing as a
"draft number":

- `latestBaselineNumber()` is the single source of truth, read from the highest-numbered
  `docs/baseline-<N>` folder.
- The draft in progress is *always* `docs/draft-<N+1>` — the baseline it is destined to become.
  It's derived, never discovered by scanning for the highest `draft-*`.
- Promotion **renames** `draft-N` to `baseline-N` and opens `draft-N+1`.

This is why `signoff` can stamp `Approved (Baseline N+1)` before promotion has happened: the
number a draft will be promoted to is known from the moment the draft exists.

A mismatched tree (say `baseline-3` alongside only `draft-6`) means an earlier promotion went
wrong. `getCurrentDraftDir()` fails fast with an explicit message rather than quietly operating
on whatever draft folder happens to have the highest number.

## Key design decisions (and why)

**Identity**
- **`signoff` takes a `name`, not a `role`.** The tool cross-checks the given name against the
  document's own declared `Owner`/`Reviewer` fields and infers which role it is — self-verifying,
  since a name matching neither is rejected outright rather than trusted at face value. If a
  document lists the same person as both Owner and Reviewer, one `signoff` call records both
  roles at once (not present in the current sample data, but the logic handles it without
  special-casing).
- **Matching is exact string equality.** "M. Fontaine" will not match an Owner of "R. Fontaine".
  That's the point: the check is only meaningful if it's strict.
- **`approve_baseline` also takes a `name`, but it's pure audit trail, not verification.**
  Nothing in this system has a "manager" field to check it against, unlike owner/reviewer.
  Logged via `console.error` (same as `notify_owner`'s stderr convention) so there's a record of
  who triggered a promotion, without pretending there's an access-control check behind it.

**Status field — three states**
- **`Draft` → `Partially Approved` → `Approved (Baseline N)`.** The first signoff moves a
  document out of `Draft`; the second completes it. `Partially Approved` carries no baseline
  number — by the time promotion is possible nothing can still be partially approved, so there's
  never a stale partial state to reason about across a baseline boundary.
- **`signoff` refuses if the document has any unresolved tracked changes at all**, checked by
  scanning for any `<w:ins>`/`<w:del>` anywhere in the file. A reviewer has to Accept/Reject in
  Word *before* calling `signoff` — this tool never touches revision markup itself, only the
  metadata table.
- **`apply_change` reverts any `Approved`/`Partially Approved` status on edit, regardless of
  which baseline number it names.** An edit to a document still showing a five-cycles-old
  `Approved (Baseline 1)` invalidates it exactly as much as editing a fresh approval would, so
  there's no baseline-number gate.
- **That revert is a plain edit, not a tracked revision.** `apply_change` also clears the
  underlying signoff record outright, so rejecting the paragraph proposal in Word must not
  silently restore a `Status` that no longer has an approval behind it. Tracked markup in the
  metadata table would also trip `signoff`'s own pending-revisions check for a change nobody
  needs to review.
- **Reverting also resets `Signoff Date` to `TBD`**, matching the value the sample documents
  already use for "not signed off". A date sitting next to `Draft` would read as a stale record.

**Unchanged documents need no signoff**
- **If a draft copy is byte-identical to its baseline copy, `signoff` is a no-op** and returns
  `{ outcome: "unchanged" }`. Those documents carry an approval that still stands; signing them
  again would *downgrade* them to `Partially Approved`, which is strictly worse than leaving them
  alone.
- Byte comparison rather than "is `Status` already Approved" because it also catches edits made
  directly in Word that bypassed `apply_change`. It's the same test `list_documents` already uses
  to decide `same` vs `CHANGED`.

**Writes are confined to the draft**
- `apply_change` and `signoff` both modify files in place, so both route through
  `draftFilePath()`, and `signoff` additionally refuses any path whose parent folder isn't the
  current `draft-<N>`. Baselines stay frozen once promoted; the baseline copy is only ever read,
  for the unchanged comparison.

**Where approval state actually lives**
- **A small JSON store, not just the docx's `Status` field.** `Status` only captures the coarse
  three-state summary; *who* approved and *when*, per role, needs its own record so
  `signoff_status` has something to report and so a second `signoff` call on the same document
  knows whether the other role already approved. Lives outside `docs/` (same reasoning as
  `notify_owner`'s log — survives the gitignored, ephemeral nature of `docs/`), in the same
  `logs/` directory, keyed by draft folder name so it can't be confused with a different cycle's
  state.
- **Synchronous read-modify-write, same as `notify_owner`'s pattern** — but worth being precise
  about why it's still safe here: `notify_owner` only ever *appends*, so concurrent calls can't
  meaningfully conflict. This store reads current state, conditionally modifies it, then writes
  it back — a real read-modify-write. It stays safe for the same underlying reason (nothing else
  can run on Node's single thread between the synchronous read and the synchronous write), but
  that's a different argument than "it's just an append", worth not glossing over.
- **The docx is saved before the store is written.** The store is the derived record and
  re-running `signoff` repairs it; a store write with no matching docx edit would report a
  phantom approval.

**Promotion**
- **Readiness requires a manifest, not just a folder scan.** `draft-N/manifest.json` must exist,
  parse to a non-empty list of `{ docId, dependsOn }`, and every `docId` it lists must have a
  matching `<docId>.docx` on disk. Then every `.docx` present must read `Approved (Baseline M)`
  for some `M`. `Draft` or `Partially Approved` on any document blocks it.
- **The manifest is a floor, not a ceiling.** Documents added to the draft since the manifest was
  written are still promoted — otherwise adding a document would be impossible, since manifests
  are only ever authored by the reindex against a baseline. The reindex regenerates the manifest
  from what actually landed.
- **Rename, don't copy.** `draft-N` becomes `baseline-N`, so a promoted draft stops existing as a
  draft and there's no dead folder left behind claiming to be work in progress.
- **No `Status` rewriting during promotion.** An untouched document keeps whatever
  `Approved (Baseline M)` it already had, even if `M` is nowhere near the new number: the
  baseline number records *when a document was actually approved*, not the folder it sits in.
  Documents signed off this cycle already carry this cycle's number, stamped by `signoff` at the
  moment both approvals landed.
- **The next draft is opened before the reindex runs.** If indexing fails, `docs/` is still
  coherent — a baseline plus a live draft — and recovers with a plain
  `npm run doc-hierarchy:ingest`. Reindexing first would leave zero `draft-*` folders on failure,
  which makes every other tool throw. The regenerated manifest is copied across afterwards so the
  new draft stays a byte-for-byte copy of the baseline.
- **Reuses the exact reindex logic `ingest.ts` already has.** `reindexLatestBaseline()` is
  extracted from `ingest.ts` as an importable function and the CLI script becomes a
  direct-execution guard around it. Since `getLatestBaselineDir()` resolves to whatever has the
  highest number, calling it *after* the rename is the entire "index the new latest" step.
- **`ingest.ts` is imported lazily**, inside `approveBaseline`. It builds a `SearchClient` and
  loads the embedding model at module scope, which the MCP server shouldn't pay for merely to
  register a tool.

**Indexing: upload first, prune after**
- The previous reindex wiped the index and repopulated it, leaving a window where search returned
  nothing. Chunk ids are stable (`<docId>-<n>`) and Azure Search uploads are upserts, so instead:
  capture the current ids, upload every chunk of the new baseline, then delete only the ids the
  new baseline doesn't cover. The index is never empty mid-run and nothing is deleted until every
  upload has succeeded.
- This is not fully atomic — mid-run a query can see new chunks for already-uploaded documents
  alongside old chunks for the rest. The airtight version is blue/green with an index alias
  (`doc-hierarchy-index-1`/`-2` behind an alias flipped on completion), which is deferred: alias
  names can't collide with index names, so it would require recreating the index under a new
  physical name and re-ingesting.

**Word lock files**
- Word leaves `~$<name>.docx` owner files beside any open document, and they end in `.docx`.
  Every folder scan goes through `listDocxFiles()`, which filters them out — otherwise promotion
  tries to read one as a document and fails.

## A consequence worth being explicit about

If a document in `draft-7` still shows `Approved (Baseline 1)` from years ago, gets edited
(reverting it to `Draft`), and is then re-signed-off with no actual content change from what
baseline 1 had — its new status is `Approved (Baseline 7)`. `signoff` doesn't look at what the
previous status was or compare content; it always stamps the current latest-baseline-plus-one the
moment both approvals land. The baseline number records *when the approval act happened*, not
whether the content changed.

## `doc-hierarchy/src/applyChange.ts` — status revert

The paragraph-matching and del/ins construction logic (the bulk of `005`) is unchanged. What's
added is an untracked metadata reset plus a signoff-record clear:

```ts
const APPROVED_OR_PARTIAL = /^(Partially Approved|Approved \(Baseline \d+\))$/;

function revertApprovalStatus(doc: Document): boolean {
  const statusCell = findTableRow(doc, "Status");
  if (!statusCell || !APPROVED_OR_PARTIAL.test(cellText(statusCell))) return false;

  replaceCellText(doc, statusCell, "Draft");
  const dateCell = findTableRow(doc, "Signoff Date");
  if (dateCell) replaceCellText(doc, dateCell, "TBD");
  return true;
}

export async function applyChange(
  filePath: string, oldText: string, newText: string,
  options: { author: string; docId: string; draftName: string }
): Promise<{ statusChanged: boolean }> {
  // ... unchanged from 005 ...
  const statusChanged = revertApprovalStatus(doc);
  await saveDocxDocument(filePath, zip, doc, docXmlPath);
  if (statusChanged) clearSignoffState(draftName, docId);
  return { statusChanged };
}
```

Naturally idempotent: a second `apply_change` against the same document finds `Status` already
reading `Draft`, so the regex doesn't match and nothing happens again.

## `doc-hierarchy/src/signoff.ts` (new)

```ts
export type SignoffResult =
  | { outcome: "unchanged"; status: string }
  | { outcome: "recorded"; role: SignoffRole; bothApproved: boolean; status: string };

export type SignoffOptions = {
  draftPath: string; baselinePath: string; docId: string;
  draftName: string; name: string; nextBaselineNumber: number;
};

export async function signoff(options: SignoffOptions): Promise<SignoffResult> {
  // 1. refuse any draftPath not directly inside the current draft-<N> folder
  // 2. no-op if draftPath is byte-identical to baselinePath
  // 3. refuse if hasPendingRevisions(doc)
  // 4. infer role from the doc's own Owner/Reviewer; reject a name matching neither
  // 5. merge into the store's state, compute bothApproved
  // 6. write Status (and Signoff Date when both are in), save docx, then persist the store
}

export function signoffStatus(draftName: string, docId: string): DocSignoffState;
```

Folder resolution stays in `mcpServer.ts`: `signoff` receives both paths rather than calling
`getCurrentDraftDir()` itself, so it's testable against temp directories.

## `doc-hierarchy/src/ingest.ts` — extract the reindex step

The top-level script body becomes an exported function plus a direct-execution guard:

```ts
export async function reindexLatestBaseline(): Promise<void> {
  const baselineDir = getLatestBaselineDir();
  const parsed = await Promise.all(listDocxFiles(baselineDir).map(f => parseFile(...)));
  const manifest = parsed.map(d => ({ docId: d.docId, dependsOn: d.dependsOn }));
  assertNoCycle(manifest);

  const previousIds = await indexedIds();
  const currentIds = new Set<string>();
  for (const doc of parsed) for (const id of await uploadDoc(doc)) currentIds.add(id);

  const stale = previousIds.filter(id => !currentIds.has(id));
  if (stale.length) await client.deleteDocuments("id", stale);

  fs.writeFileSync(path.join(baselineDir, "manifest.json"), JSON.stringify(manifest, null, 2));
}

// Only when run directly (npm run doc-hierarchy:ingest), not when approve.ts imports it.
if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
  await reindexLatestBaseline();
}
```

`pathToFileURL`, not string-concatenated `file://` — the latter never matches on Windows.

## `doc-hierarchy/src/approve.ts` (new)

```ts
/** Manifest present and complete, and every document on disk already Approved. */
export async function assertPromotable(draftDir: string): Promise<string[]>;

export async function approveBaseline(): Promise<PromotionResult> {
  const baselineNumber = latestBaselineNumber() + 1;
  const draftDir = getCurrentDraftDir();            // docs/draft-<baselineNumber>
  const files = await assertPromotable(draftDir);

  const baselineDir = path.join(packageRoot, "docs", `baseline-${baselineNumber}`);
  fs.renameSync(draftDir, baselineDir);

  const newDraftDir = path.join(packageRoot, "docs", `draft-${baselineNumber + 1}`);
  fs.mkdirSync(newDraftDir, { recursive: true });
  for (const f of fs.readdirSync(baselineDir)) copy(baselineDir, newDraftDir, f);

  const { reindexLatestBaseline } = await import("./ingest.js");
  await reindexLatestBaseline();                    // resolves to baselineDir

  copy(baselineDir, newDraftDir, "manifest.json");  // regenerated by the reindex
  return { baselineName, draftName, docCount: files.length };
}
```

`assertPromotable` is split out so the validation is testable without a live search index.

## Known risks / not exercised

- Everything `005` already flagged about OOXML round-trip fidelity applies to `signoff`'s
  `Status`/`Signoff Date` edit, which goes through the same `replaceCellText` path. Promotion
  itself touches no XML (rename plus file copies), so there's no round-trip risk there.
- **`approveBaseline` end-to-end is untested** — the rename/copy sequence can't run without a live
  Azure Search index for the reindex. Only `assertPromotable` has coverage. Making the reindex
  injectable would close this.
- **Promotion isn't atomic.** If the reindex fails, `docs/` is coherent but the index and the
  baseline manifest are stale; recovery is a manual `npm run doc-hierarchy:ingest`.
- **`doc-hierarchy-signoffs.json` accumulates entries for superseded drafts** — nothing prunes a
  draft's records once it's been promoted. Harmless (nothing reads an old draft's key) but grows
  unbounded over many cycles.
- **Same-person-both-roles** is handled in the logic but doesn't occur in the current 5-document
  sample set, so it's untested in practice.
- The signoff store's read-modify-write safety argument is sound but worth re-confirming if this
  ever moves off a single synchronous Node process.
