# 010 — `ask_documents`: answer questions across the whole corpus

**Scope:** `doc-hierarchy` only. Read-only — no writes, no OOXML, nothing destructive. Lowest-risk
addition in this series so far.
**Relates to:** `graph.ts` (`downstreamOf`, unchanged, reused as-is), `rag-api`'s `/search`
(unchanged — this closes a gap purely client-side), `000.hackathon-setup.md` (confirms `score`
is already in every hit).

**The idea:** answer a free-text question like "what is the braking distance" against the
current baseline's whole indexed content, and return passages the calling model can synthesize
an answer from — including passages that don't restate the value but discuss or constrain it
(e.g. "the required braking distance agreed upon should never be changed without notice"), and
passages in documents that are relevant only because of their position in the dependency graph,
not because their wording resembles the question at all.

---

## Key design decisions (and why)

- **"States the value" vs. "discusses the topic without stating it" is left entirely to the
  calling model — the tool does not try to classify this.** A passage like "the required braking
  distance agreed upon should never be changed without notice" shares enough vocabulary with
  "what is the braking distance" that it can score just as high, or higher, than a passage that
  actually states "750m" — vector similarity captures topical relevance, not whether a specific
  fact is present in the text. Any score-threshold split built to separate these would be
  guessing at something embeddings aren't suited to distinguish. This is a reading-comprehension
  judgment, and every other tool in this project already defers exactly this kind of judgment to
  the calling model (`suggest_changes` doesn't decide whether a match is "close enough" either —
  it returns the passage and lets the reader decide).
- **What retrieval *can* do reliably is find passages that wouldn't surface by wording alone —
  that's the graph's actual job here.** A document downstream of a direct source can be relevant
  through dependency even when it shares almost no vocabulary with the query (a test spec that
  says "verify compliance with CMP-SIG-101" without ever using the words "braking" or
  "distance"). That's a distinct, checkable claim retrieval can make, unlike the
  states-it-vs-discusses-it distinction above.
- **So there are two genuinely different axes, and only one belongs in this tool**: *how a
  passage relates to the question's content* (not this tool's job) vs. *how the tool found the
  passage* (plain search vs. surfaced via the dependency graph — this tool's actual job). The
  previous draft of this doc conflated the two under one "direct/indirect" label; this revision
  keeps only the second.
- **A candidate found via the graph is still checked against the query independently before
  being included** — being downstream of a relevant document doesn't make a document relevant.
  Same principle `suggest_changes` already relies on ("the graph gives the candidate set, RAG
  does the filtering"), applied here to reads. Without this check, a downstream document like
  `SUB-TRAC-020` (about acceleration, not braking) would surface for a braking-distance question
  purely by graph proximity.
- **Downstream only, not upstream** (see Open decisions) — a document upstream of a relevant hit
  is where a fact likely originated, and in practice probably already surfaces in the plain
  search on its own merits, since it states the thing outright.
- **`suggest_changes` gets the same score-floor fix**, closing the gap flagged back in `004` —
  same underlying mechanism, no reason to leave it half done now that this tool needs the
  identical pattern anyway. `rag-api`'s `/search` already returns `score` on every hit, so this
  is a client-side filter in `doc-hierarchy`, no change to the shared service.

## Open decisions (defaults applied, not confirmed)

- **Downstream-only graph traversal** — if a fact's *origin* matters as much as where it's used,
  upstream traversal from a hit is the same shape of change, calling the graph logic in the
  other direction (which doesn't exist yet and would need its own small function).
- **The plain-search relevance floor is an untested placeholder** (`0.55`) — same caveat as
  every prior MiniLM-score mention in this project: verify the actual gap between relevant and
  irrelevant passages against real data before trusting this number. Set too high, it could
  exclude a valid "discusses without stating" passage like the example above, crowding it out
  in favor of nothing; set too low, results get noisy.

## `doc-hierarchy/src/ask.ts` (new)

```ts
import { loadGraph, downstreamOf } from "./graph.js";

const RAG_API_URL = process.env.RAG_API_URL ?? "http://localhost:8000/search";
const INDEX = "doc-hierarchy-index";

// Untested placeholder — calibrate against real data. One floor for the plain search:
// a passage that states the value and one that discusses the topic without stating it can
// score similarly, so this deliberately doesn't try to separate them (see design decisions).
const SEARCH_MIN_SCORE = 0.55;
const GRAPH_MIN_SCORE = 0.5; // for the independent relevance check on a graph candidate

type Hit = { docId: string; content: string; source: string; score: number };

function odataEscape(s: string): string {
  return s.replace(/'/g, "''");
}

async function search(query: string, top_k: number, filter?: string): Promise<Hit[]> {
  const res = await fetch(RAG_API_URL, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ index: INDEX, query, top_k, filter }),
  });
  const { results } = (await res.json()) as { results: Hit[] };
  return results;
}

export type AskResult = {
  found: Hit[];                              // plain search — may state the value or just discuss it
  viaGraph: (Hit & { downstreamOf: string })[]; // surfaced only via dependency, checked independently
};

export async function askDocuments(query: string): Promise<AskResult> {
  const raw = await search(query, 8);
  const found = raw.filter(h => h.score >= SEARCH_MIN_SCORE);

  const graph = await loadGraph();
  const foundIds = new Set(found.map(h => h.docId));
  const viaGraph: AskResult["viaGraph"] = [];
  const seen = new Set<string>();

  for (const hit of found) {
    const candidates = downstreamOf(graph, hit.docId).filter(id => !foundIds.has(id) && !seen.has(id));
    for (const docId of candidates) {
      const [best] = await search(query, 1, `docId eq '${odataEscape(docId)}'`);
      if (best && best.score >= GRAPH_MIN_SCORE) {
        viaGraph.push({ ...best, downstreamOf: hit.docId });
        seen.add(docId);
      }
    }
  }

  return { found, viaGraph };
}
```

## `doc-hierarchy/src/mcpServer.ts` — new tool

The description explicitly asks the calling model to make the states-it-vs-discusses-it call
itself, since the tool deliberately doesn't:

```ts
import { askDocuments } from "./ask.js";

server.registerTool(
  "ask_documents",
  {
    description:
      "Search the current baseline for passages relevant to a question. Some returned " +
      "passages may state the answer directly; others may only discuss, reference, or " +
      "constrain the topic without stating a specific value — read each passage and decide " +
      "which it is before answering. Passages under 'found via dependency graph' were " +
      "surfaced because they're downstream of a relevant document, not because their wording " +
      "resembles the question — they may use entirely different vocabulary.",
    inputSchema: { question: z.string() },
  },
  async ({ question }) => {
    const { found, viaGraph } = await askDocuments(question);
    if (found.length === 0) {
      return { content: [{ type: "text" as const, text: "No relevant documents found." }] };
    }
    const foundText = found.map(h => `[${h.docId}] ${h.content}`).join("\n---\n");
    const graphText = viaGraph.length
      ? "\n\nFound via dependency graph (downstream of a relevant document, wording may differ entirely):\n" +
        viaGraph.map(h => `[${h.docId}, downstream of ${h.downstreamOf}] ${h.content}`).join("\n---\n")
      : "";
    return { content: [{ type: "text" as const, text: foundText + graphText }] };
  }
);
```

No changes needed in `mcp-manager` — a new tool on an already-managed server is picked up the
next time its tool list is refreshed (a restart of `doc-hierarchy`), same as any other new tool.

A good result: `found` includes whichever passage states `750m` outright, and — if the sample

should never be changed without notice" that discusses the same topic without restating the
number. A good final answer from the calling model distinguishes the two ("750m, per
`CMP-SIG-101`; note `SYS-REQ-001` also states this value can't be changed without notice")
rather than treating every returned passage as equally answering the question. `viaGraph` should
surface a document like `TST-SIG-201` if its test-case wording doesn't share vocabulary with the
question, and should not surface `SUB-TRAC-020` (about acceleration), the same test case this
project has used from the start for "graph-connected but not actually relevant."

## Known risks / not exercised

- **Score thresholds are untested placeholders** — the most important thing to check before
  relying on this.
- **A real failure mode worth watching for**: if several passages score above the floor but
  none of them actually states the value, and a genuine "discusses without stating" passage like
  the example above doesn't even make the top-8 plain search, the calling model has nothing to
  work with — there's no fallback search with a wider net built in here.
- **N+1 query pattern**: one `rag-api` call for the initial search, plus one more per graph
  candidate. Fine at this project's scale, would need batching at a larger corpus size.
- **The same query text gets re-embedded once per candidate check** rather than computed once
  and reused — not a repeated model load (`004`'s caching prevents that), but repeated inference
  work. Removing this would need `rag-api` to accept a pre-computed vector instead of re-embedding
  a query string each call — a shared-service change out of scope here.
- **A document could be genuinely relevant without being graph-connected to anything in `found`**
  (two independently-written documents that happen to state related facts) — this design has no
  way to surface that case; it would only appear if it happens to clear the plain search floor
  on its own.
