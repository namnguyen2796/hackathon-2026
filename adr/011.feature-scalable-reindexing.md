# 011 — scalable reindexing: blue/green swap + incremental hashing

**Scope:** `doc-hierarchy` only.
**Relates to:** `004` (original wipe-then-reindex `ingest.ts`), `008` (flagged blue/green as
deferred — this is that work), `009` (`workspaceRoot()`), `010` (`ask_documents`'s N+1 pattern,
fixed here too).

**The idea:** at 5 one-page documents, wiping and fully re-embedding the whole index on every
promotion is invisible. At hundreds of documents of tens-to-hundreds of pages, it's a real
availability gap (the index is empty or partial mid-reindex) and a real cost (everything gets
re-embedded even when almost nothing changed). This replaces wipe-then-reindex with an
alias-based blue/green swap, adds content-hash-based skipping so unchanged documents don't get
re-embedded, and fixes three smaller issues found while reasoning through what actually breaks
at scale.

---

## Key design decisions (and why)

- **An index alias, not a second index name in application code.** `doc-hierarchy-index`
  becomes an alias pointing at one of two fixed physical indexes
  (`doc-hierarchy-index-blue`/`-green`). `rag-api`, `suggest_changes`, and `ask_documents` keep
  referencing `"doc-hierarchy-index"` exactly as before and never know a swap happened — this is
  the reason the design is low-risk despite touching the reindex path, not just a nice property.
  Verified aliases work on the free tier (Microsoft's own docs: "any region and pricing tier";
  the one tier restriction found is specific to role-based access, which doesn't apply here
  since this project authenticates with an admin key).
- **The alias only flips once the new content is fully uploaded — that's the whole fix for the
  availability gap.** No window where a caller sees an empty or half-populated index.
- **Unchanged documents are detected by comparing content hashes against the *previous*
  baseline's manifest, not by touching the search index's schema.** Each baseline's
  `manifest.json` already exists per document; adding a `contentHash` field to it is a small,
  natural extension. If a document's hash matches what the previous baseline recorded for the
  same `docId`, its already-embedded chunks are copied from the live index straight into
  staging — no re-parsing, no re-embedding.
- **A genuine gotcha worth flagging up front**: this only skips *re-embedding*, not
  *re-chunking*. If the chunking strategy itself changes (step 12 below changes it, in this same
  doc), an unchanged document's copied-over chunks still reflect the *old* chunking scheme
  forever, since a hash match means it's never touched again. One full re-embed with hashing
  temporarily disabled is needed whenever chunking logic changes, to let every document pick up
  the new scheme once.
- **Peak storage roughly doubles during a swap** (old and new index both hold data until the old
  one gets reused). Trivial today; worth budgeting for deliberately once approaching the 50MB
  free-tier cap.

## Code

### Steps 5, 9 — `doc-hierarchy/src/indexAlias.ts` (new)

```ts
import { SearchIndexClient, AzureKeyCredential } from "@azure/search-documents";

const ALIAS = "doc-hierarchy-index";
const PHYSICAL_INDEXES = ["doc-hierarchy-index-blue", "doc-hierarchy-index-green"] as const;

const indexClient = new SearchIndexClient(
  process.env.AZURE_SEARCH_ENDPOINT!,
  new AzureKeyCredential(process.env.AZURE_SEARCH_KEY!)
);

/** live = whatever the alias currently points to; staging = the other one of the fixed pair. */
export async function getLiveAndStagingIndexNames(): Promise<{ live: string; staging: string }> {
  const alias = await indexClient.getAlias(ALIAS);
  const live = alias.indexes[0];
  const staging = PHYSICAL_INDEXES.find(name => name !== live);
  if (!staging) throw new Error(`Alias "${ALIAS}" points to an unexpected index: ${live}`);
  return { live, staging };
}

export async function swapAliasToStaging(staging: string): Promise<void> {
  await indexClient.createOrUpdateAlias({ name: ALIAS, indexes: [staging] });
}

export { ALIAS, PHYSICAL_INDEXES, indexClient };
```

### Step 6 — `doc-hierarchy/src/contentHash.ts` (new)

```ts
import { createHash } from "node:crypto";

export function contentHash(text: string): string {
  return createHash("sha256").update(text).digest("hex");
}
```

### Steps 7, 8, 9, 10 — `doc-hierarchy/src/ingest.ts` (rewritten core)

Presented as new/changed logic rather than a full reconstructed file, since the exact current
body isn't available in this pass — `parseFile`, `assertNoCycle`, `embed()`, and the metadata
parsing stay as they are; what changes is everything downstream of parsing:

```ts
import { getLatestBaselineDir, workspaceRoot } from "./baselines.js";
import { getLiveAndStagingIndexNames, swapAliasToStaging, ALIAS, indexClient } from "./indexAlias.js";
import { contentHash } from "./contentHash.js";
import { SearchClient, AzureKeyCredential } from "@azure/search-documents";

const credential = new AzureKeyCredential(process.env.AZURE_SEARCH_KEY!);
function clientFor(indexName: string) {
  return new SearchClient<HierarchyDoc>(process.env.AZURE_SEARCH_ENDPOINT!, indexName, credential);
}

async function recreateIndexSchema(indexName: string, schema: SearchIndex) {
  try { await indexClient.deleteIndex(indexName); } catch { /* fine if it didn't exist yet */ }
  await indexClient.createIndex({ ...schema, name: indexName });
}

async function copyExistingChunks(docId: string, live: string, staging: string): Promise<boolean> {
  const results = await clientFor(live).search("*", { filter: `docId eq '${docId.replace(/'/g, "''")}'` });
  const docs: HierarchyDoc[] = [];
  for await (const r of results.results) docs.push(r.document);
  if (!docs.length) return false;
  await clientFor(staging).uploadDocuments(docs);
  return true;
}

/** Previous baseline = current latest - 1. Missing file or missing docId both mean "treat as
 *  changed" — safer to over-embed on the first run of this scheme than to skip incorrectly. */
function readPreviousHashes(baselineDir: string): Map<string, string> {
  const n = Number(path.basename(baselineDir).match(/-(\d+)$/)?.[1]);
  const prevPath = path.join(workspaceRoot(), `baseline-${n - 1}`, "manifest.json");
  if (!fs.existsSync(prevPath)) return new Map();
  const prev: { docId: string; contentHash?: string }[] = JSON.parse(fs.readFileSync(prevPath, "utf-8"));
  return new Map(prev.filter(d => d.contentHash).map(d => [d.docId, d.contentHash!]));
}

export async function reindexLatestBaseline(): Promise<void> {
  const baselineDir = getLatestBaselineDir();
  const files = fs.readdirSync(baselineDir).filter(f => f.endsWith(".docx"));
  const parsed = await Promise.all(files.map(f => parseFile(path.join(baselineDir, f))));

  const manifest = parsed.map(d => ({
    docId: d.docId,
    dependsOn: d.dependsOn,
    contentHash: contentHash(d.text),
  }));
  assertNoCycle(manifest);

  const { live, staging } = await getLiveAndStagingIndexNames();
  await recreateIndexSchema(staging, HIERARCHY_INDEX_SCHEMA); // the schema object from createIndex.ts

  const previousHashes = readPreviousHashes(baselineDir);

  for (const doc of parsed) {
    const hash = contentHash(doc.text);
    const unchanged = previousHashes.get(doc.docId) === hash;
    const copied = unchanged && (await copyExistingChunks(doc.docId, live, staging));
    if (!copied) await uploadDoc(doc, staging); // uploadDoc takes a target index name now
  }

  await swapAliasToStaging(staging);

  fs.writeFileSync(path.join(baselineDir, "manifest.json"), JSON.stringify(manifest, null, 2));
  console.log(`Reindexed ${parsed.length} docs into ${staging}. ${ALIAS} now points there.`);
}
```

`uploadDoc(doc, indexName)` is the existing per-document chunk/embed/upload function from `004`,
adjusted to take a target index name instead of always writing to one hardcoded client.

### Step 14 — bounded concurrency helper

```ts
async function processInBatches<T>(items: T[], batchSize: number, fn: (item: T) => Promise<void>) {
  for (let i = 0; i < items.length; i += batchSize) {
    await Promise.all(items.slice(i, i + batchSize).map(fn));
  }
}
```

## Known risks / not exercised

- **`search.in()`'s exact syntax (step 13) is unverified** — flagged inline above, repeated here
  since it's a real gap, not a formality.
- **The chunking-change interaction (see design decisions)** is a real trap: changing chunking
  strategy and shipping hash-based skipping in the same release means unchanged documents never
  get re-chunked under the new scheme until hashing is bypassed once, deliberately.
- **Alias limits**: max aliases scales with max indexes per tier (roughly double, on services
  created after October 2022) — not a concern at 2 aliases needed, but worth knowing if this
  pattern gets reused for `docs-search` or a future project too.
- **None of this has been run against a real reindex cycle** — the alias mechanism, the
  hash-comparison logic, and the copy-existing-chunks path are all new and untested together.
